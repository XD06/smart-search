# 声称拆解指南 (Claim Breakdown)

用于 **B 型输入**（用户转述一个说法/帖子/观点，如"据说…"、"看到一个说法…"）。

核心原则：**先行推测，后行补充**——字面声称立即核查（主线程），暗含推测只存不查（副线程），用户追问触发才深挖。

## 为什么需要这一步

| 风险 | 后果 |
|------|------|
| 直接采信用户转述 | 把未验证的说法当既定前提，答案从源头就错 |
| 拿原话整句去搜 | 回声室：搜到的全是同一说法的搬运，互相"交叉验证"只是复读 |
| 暗含推测全查 | 大量时间花在用户不关心的方向上 |

## 拆解四步

### 步骤 1：拆出字面声称（主线程）

逐句扫描，每个**可证伪**的原子声明单独一项。可证伪 = 有明确对象、能被一手信源证实或证伪。不可证伪的（"被低估"这类评价）转入"证据基"核查。

### 步骤 2：类型标注

用 Level 2 的声称类型学逐项标注（实体/数字/政策/观点/比较），决定核查去向：

| 类型 | 核查去向 |
|------|----------|
| 实体存在性 | 官网/Docs 直接判存在 |
| 数字/额度 | 官方 Rate Limits/Pricing，必查口径 |
| 政策/规则 | Docs 条款 + 社区实测差异 |
| 观点/评价 | 社区声量与对比数据（证据基） |
| 比较级 | 双方一手数据拉齐 |

### 步骤 3：生成暂存线索（副线程，只列不查）

从"用户为什么给我看这个"推测真实需求。**不要把推测当结论，也不要立即搜索。**

每条暂存线索的格式：`假设：用户可能关心 X → 若追问则查 Y`

### 步骤 4：输出分流

- 主线程：字面声称认真核查，进证据表
- 副线程：暂存线索放输出末尾，一行一条，等用户后续提问命中再升级

## 常见信号速查（步骤 3 用）

| 话面信号 | 常见真实需求（暂存假设） |
|----------|--------------------------|
| 免费/额度/白嫖/不要钱 | 成本敏感，可能在评估批量使用或套利空间 |
| 被低估/没人知道/真心推荐 | 掌握信息差，有求验证动机 |
| 对比 A 和 B / 哪个更值得 | 选型决策，需要按场景给出推荐 |
| 亲测/已用 X 个月 | 想要长期使用报告，不只是参数 |
| 翻车/求助/避坑 | 排障需求，优先找同类问题案例 |
| 贴数据/榜单/截图 | 想确认数据真实性，同时想知道数据背后含义 |

## 实例 1：推荐型转述（五层完整标准格式）

> ⚠️ **以下为虚构示例**：模型名 `gemini-3.5-flash-lite` 与"每天 500 次"额度均为演示用编造内容，**不是真实事实**，禁止当作已知事实引用或写进答案。

> 所有拆解实例统一按以下五层呈现：**层一"字面信息"是主线程，立即核查；层二至五是副线程，只存不查**，用户后续提问命中哪条才深挖哪条。

### 输入

> 说一个被大家低估的模型，gemini-3.5-flash-lite，即使一个免费的账号都有每天500次的API额度。

### 一、字面信息（可核查的真伪点）—— 主线程，立即核查

| 声明 | 核查点 |
|------|--------|
| 模型名 gemini-3.5-flash-lite | 是否真实存在？版本号、命名是否准确（Flash-Lite 是轻量定位） |
| 免费账号每天 500 次 API 额度 | Google AI Studio 免费层实际限额是多少？"次"的定义（请求数？还是 token？） |
| "被大家低估" | 这是观点不是事实，需要社区声量数据验证其证据基 |

**进 Checklist 时每行必须带目标信源**：实体 → 官网模型列表；数字/额度 → 官方 Rate Limits 页；观点 → 社区声量与独立对比。

### 二、表面暗含的信息（说话者画像与动机）—— 副线程，暂存

这段话表面在分享信息，实际在传递几层意思：

1. **成本信号**：说者在做成本敏感型批量任务——500 次/天免费额度意味着一个月 1.5 万次调用，正常商业 API 这是几十上百美元的流水。他关心的是"免费额度能干多少活"。
2. **需求暗示**：他可能在评估把这个模型用于生产或自动化流程（爬虫摘要、内容生成、数据标注、Agent 的轻环节），不是在"尝鲜"。
3. **认知锚点**："被低估"暗示他认为多数人在用贵模型干轻活——他掌握了一个信息差，且有炫耀/求验证的混合动机。

### 三、不为人知的一面（真实约束，往往和表面宣传相反）—— 副线程，暂存

免费额度 500 次的说法背后，通常藏着这些：

- **数据政策**：免费层 API 的请求数据大概率被用于训练（Google 一贯政策），用于涉密/隐私任务有合规风险——这条永远不会出现在宣传语里
- **隐性限流**：写 500 次，实际可能受 RPM/并发/排队限制，高峰时段降智或返回 429
- **能力阉割**：Lite 档通常在长上下文、多模态、指令遵循上缩水——"够用"的边界很窄，幻觉率对轻任务是否可接受需要实测
- **可持续性**：互联网公司的免费额度随时可收回或改政策，今天 500 次不等于三个月后还有

### 四、推测的信息（需要外部验证的假设链）—— 副线程，暂存

- **Google 的战略意图**：用免费额度换开发者生态和市场份额，对抗 OpenAI/Anthropic——如果属实，短期会维持，长期可能收紧
- **套利空间**：如果额度真实且宽松，可能出现"免费额度 + 中转 API"灰产，这会加速官方风控收紧
- **同类对比**：这句话隐含"免费 LLM 额度"是一个品类对比问题——OpenRouter 免费档、国产模型免费额度等，谁的免费策略最划算

### 五、用户想获得什么（意图推断）—— 副线程，暂存

用户把这段话丢过来，真实需求几乎可以肯定是：

1. 这是不是真的、今天能不能用（真伪 + 可落地性）
2. 怎么用最值——什么任务适合 Lite 档、怎么把 500 次/天榨出最大价值
3. 有什么坑——数据训练、限流、封号风险，别让产品踩雷
4. （隐含）有没有更划算的替代方案

### 最终输出长这样（模板 E）

- **层一** → 结论（真/部分真/假/无法证实）+ 证据表 + **口径修正**（"500 次"的真实定义、适用条件）
- **层二至五** → 压缩成输出末尾的「暂存线索」，每条一行，例如：
  - 想要同类免费额度横向对比？说一声
  - 关心免费层数据是否用于训练/限流细则？说一声
  - 想评估 Lite 档能否上生产？说一声

### 这个示例不会做的事

- 不搜「gemini-3.5-flash-lite 每天500次」原话，全部绕回一手信源
- 不把"被低估"当事实证真/证伪，转而查社区声量与独立对比
- 不在用户开口之前把四条假设全查一遍——只列，不查
